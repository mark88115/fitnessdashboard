### fitness-dashboard — 3D InBody 健身成果儀表板

靜態網頁(HTML/JS/Three.js),將 InBody 身體組成掃描歷史視覺化成 3D 人形,搭配可拖曳雙把手日期時間軸、飲食(-30%~+30%)與訓練(-30%~+100%)預估滑桿、預估期間與重訓資歷下拉選單、左右數據面板、可收合詳細面板、含 tooltip 的趨勢圖。

- 進入點:`fitness-dashboard/index.html`(需從專案根目錄起 local server,例如 `python -m http.server 8000`,再開 `http://localhost:8000/fitness-dashboard/`——因為會讀取根目錄的 `workout/` 資料)
- 使用者資料:`workout/<user>/data.json`、`workout/users.json`
- 詳細使用/測試說明見 `fitness-dashboard/README.md`
- **預估模型 = 個人歷史趨勢(線性回歸)+ 逐週熱量平衡模擬**(`projection.js` 的 `simulateEnergyBalance`)。滑桿 0%/0% 時熱量收支為零,結果就退回純趨勢,不會重複計算
  - 每週重算:攝取 = `recommended_kcal`×(1+飲食%);維持 = `recommended_kcal` + 額外訓練消耗 + 13×已增肌肉kg + 4.5×已增脂肪kg(新肌肉會墊高基礎代謝,所以增肌會自己踩煞車)
  - **「目前訓練值多少熱量」是從使用者自己的 InBody 推出來的**:`(recommended_kcal − bmr_kcal×1.2) × 0.5`(1.2 = 久坐活動係數,0.5 = 假設活動量有一半來自刻意訓練)。poya 約 301 kcal/天 = 訓練滑桿 +100% 的重量
  - 肌肉增長受**熱量供給閘控**:赤字 500 kcal/天時增肌歸零,1000 時開始掉肌肉。所以「只加訓練不加飲食」會減脂但增肌打折,而「-30% 飲食 + 100% 訓練」反而掉最多肌肉——這正是舊模型(訓練只加肌肉、完全不耗熱量)做不到的交互作用
  - **增肌上限用 Lyle McDonald 資歷表**(第1年 10.15、第2年 4.95、第3年 2.5、第4年+ 1.15 kg/年,取區間中值),UI 有「重訓資歷」下拉選單。把該表視為「最緊繃訓練」的天花板,**使用者目前的訓練量假設為天花板的 50%**,所以滑桿 +100% = 天花板、0% = 現狀
  - ⚠️ **滑桿給的是「相對現狀的增量」,不是絕對值**:0% 時增量為零、退回純個人趨勢。**不要改成直接用 Lyle 值當絕對增肌量**——趨勢裡已經含有目前訓練的成果,會重複計算
  - 🔑 **這個設計讓模型可以自我檢查**:把滑桿歸零、比對「個人趨勢的年增肌」與「所選資歷 × 50% 的理論值」,兩者應該接近。差太多就表示資歷選錯了(poya 實測趨勢約 4kg/年,對應第1年的 5.1kg,而非預設的第2年 2.5kg)
  - **儲存效率**:熱量盈餘只有 50% 變成脂肪(食物產熱效應 + NEAT;Levine 過度餵食研究)。**赤字方向不打折**,兩者機制與幅度不同,合併成一個常數會把這件事藏起來 → 模型「減得比增得快」是刻意的
  - 體脂設有 4% 必需脂肪地板,避免長期極端赤字算出不可能的身體組成
  - ⚠️ 仍**標註「僅供參考」**:資料點少、常數取自文獻平均值(每公斤脂肪 7700 kcal、肌肉 1800 kcal、肌肉靜態代謝 13 kcal/kg/天),未針對個人校準

- 🏆 **這是使用者第一個用 AI 完成的作品**(2026-08-01 定案)
- **版面**:左欄個人基本狀態(身高/體重/年齡/性別,來自 `data.json` 頂層欄位)+ 各部位數據 + 標準參考值(浮動彈出,不擠壓版面);中間兩個 3D 視窗——左「使用者當下狀態」(基準/目前/預估三態疊在同一位置,灰/綠/紫,三態各有獨立顯示開關)、右「身材參考」(體脂 5~40%、肌肉量率 70~160% 兩條拉桿 + 即時肌肉量 kg/預估體重,全部依使用者實際身高換算)
- **三態的疊圖方式是刻意不對稱的**:`projected` 開深度測試 + 高不透明度(0.8),所以紫色**只畫在「預估比目前突出」的地方**——既銳利又帶有意義(紫色 = 會長大的部位);`baseline` 則關閉深度測試 + 低透明度(0.22),因為基準通常**比目前小**,開了深度測試會整個縮在目前的身體內部、完全畫不出來。⚠️ **不要為了「統一」把 baseline 也改成深度測試**
  - 附帶結論:紫色看不清楚時**調不透明度是沒用的**——關閉深度測試的圖層會無差別蓋滿整個輪廓,提高不透明度只是把整隻塗成一色(實測 0.45 會變成混濁藍灰)。要清楚就得靠深度測試
- **3D 初始視角**:`CAMERA_POSITION = [0, 1.0, 3.15]`、`CAMERA_TARGET = [0, 0.88, 0]`(視點設在身體實際中心高度,放大後才會置中)。垂直 fov 35° 下可視高度 = 2·d·tan(fov/2),人形高 1.731 → 佔畫面 **87%**(原本距離 4.5 只佔 61%,人小、周圍一大片空白)。只是起始視角,OrbitControls 照常接手
- ⚠️ **兩個視窗吃完全相同的兩個數值:肌肉量率 + 真實體脂率**,共用同一個 `archetypeWeights()`。所以把右邊拉桿調到跟左邊某一態相同的數字,兩邊人形就會長一樣(實測預估態 buff 0.404 vs 右邊 0.400)。**左邊不可以改回用「5 部位 musclePct/fatPct 平均」**——那是 InBody 的「佔標準%」,跟右邊拉桿的體脂率是不同量綱,曾造成同樣體態左右差 1.65 倍。左邊的肌肉量率由 `muscleRateFromSmm(smmKg, heightCm)` 從骨骼肌重反推,體脂率直接用 `pbfPercent`
- ⚠️ **雙軸各自獨立:肌肉軸只驅動 buff/thin,脂肪軸只驅動 fat/thin**。**不要改回「在二維空間找最近體型」的聯合 IDW 混合**:normal 座落在那個空間的正中央,實務範圍內幾乎永遠是最近的錨點,會把差異整個吃掉——用真實 InBody 歷史量測,基準/目前/預估三態的 buff 權重是 0.031 / 0.033 / 0.090,**前兩者只差 0.002,等於三個月的真實進步在畫面上完全看不出來**
- ⚠️ **`buff.musclePct = 160` 必須跟 `bodytypeExplorer.js` 的 `MUSCLE_MAX` 一致**(拉桿拉到底 = 剛好是 buff 模型本身的樣子)。曾經一邊寫 200、一邊用拉桿上限 160,就是上面那個 1.65 倍差距的來源
- **3D 模型**:MakeHuman 產生的瘦/正常/胖/超壯 4 種體型(`fitness-dashboard/assets/models/bodytypes/*.dae`)當 Three.js morph target 混合,取代早期「單一模型 + 骨骼縮放」(先後試過 `BaseMeshMale.glb`、`HumanBasemeshRigged.glb`,都已刪除)。取捨:換掉了逐部位獨立縮放,現在没辦法呈現「手臂粗但腿細」這種不對稱體型
- **關鍵技術**:4 個 `.dae` 是同一份 MakeHuman 拓樸,`ColladaLoader` 解析後頂點數與順序完全一致(已驗證),可直接互當 morph target
- **體型校準**:musclePct/fatPct 座標定義在 `bodyScene.js` 的 `BODYTYPE_MODELS`;MakeHuman 匯出腳本(`MakeHuman/makehuman-1.3.0/makehuman/plugins/zz_auto_export.py`,啟動時自動匯出)與踩過的坑寫在 `fitness-dashboard/README.md`。MakeHuman 專案在 `C:\Users\User\Desktop\MakeHuman\`(repo 外)
- ⚠️ **`buff.dae` 必須用 `muscle=1.0, weight=0.9` 匯出**。原本是 `weight=0.2`,低 weight 把身體縮小、剛好抵銷肌肉增加,量測出來「超壯」跟 normal 的平均頂點位移只有 0.0343,**比「瘦」的 0.0487 還小**——素材裡根本沒有「變大」的訊號。改成 weight=0.9 後是 0.0723。**不要試著用程式放大混合權重來補救**(morph influence 超過 1.0、或從位移場合成額外體積):那是在放大一個中位數為 0 的空訊號,只會產生摺角和一塊塊分離的肌肉。體積要由素材提供
- ⚠️ **morph 必須同時提供 `morphAttributes.normal`**,不能只給 position。Three.js 只內插有給 target 的屬性,只給位置的話體型變了但法線還停在原始模型,等於用錯的表面朝向算光照。霧面材質看不出來,一加高光就出現多邊形色塊
- ⚠️ **算法線不能直接用 `computeVertexNormals()`** — 這個網格是非索引的(13380 頂點被拆成 80268),那個方法會讓每個三角形各自持有法線 → 整個人變成稜角狀平面著色。要**先依位置焊接再平均**(見 `bodyScene.js` 的 `computeNormalsFor`)
- **打光決定肌肉線條看不看得見**:環境光 0.35(原本 1.1 會把形狀陰影全填平)、主光 2.2 從側前方斜射(正面光最不利立體感)、暖色補光 0.7 從後方勾邊;材質 `roughness: 0.32`(預設 1.0 是純霧面、零高光,而高光正是描出曲面的東西)。自身陰影(shadow map)試過會在大腿產生 shadow acne 條紋,增益小於副作用,**刻意不採用**

#### 手機版

- **版面由 `<html data-layout="desktop|mobile">` 驅動,不是直接用 media query**(`layoutMode.js`)。沒點過就照螢幕寬度自動判斷,標題列最左邊有 `電腦版|手機版` 開關可以鎖定並記住;鎖定手機版時整頁會框成 400px 寬置中,不然在寬視窗看堆疊版面等於沒看到。**這個開關是為了讓「改手機版」不用每次手機拍照傳來傳去**
- **順序**:標題列 → 個人+各部位數據 → 詳細數據 → 趨勢圖 → 時間軸 → 當下狀態人形 → 飲食/訓練滑桿 → 身材參考人形 → 體脂/肌肉拉桿。**每個控制項都貼著它控制的那個人形**(時間軸在人形上面、滑桿在人形下面),因為桌機版的排法在手機上會讓兩者相隔一個螢幕
- 時間軸與滑桿區是 `layoutMode.js` **搬 DOM 節點**進 `.center-panel`,不是用 `display: contents` 溶容器 —— 溶掉會連容器的背景邊框 padding 一起失效,試過一次整個版面垮掉
- ⚠️ **每個頂層區塊都帶著桌機版置中用的 `margin-inline: auto`,而 auto margin 會取消 flex item 的 stretch**,一變成 flex item 就會縮成內容寬度飄在中間(時間軸實測 262px / 框寬 398)。**這就是上面那次「整個垮掉」的真正原因** —— 不是 `display: contents` 本身,是所有橫幅同時縮水。改手機版時務必一併驗證「每個區塊寬度是否滿版」與 `scrollWidth <= clientWidth`
- 個人基本狀態排成兩欄(身高|體重 / 年齡|性別),各部位數據排成一行(標籤+數值同列):數據面板 855px → **352px**
- 觸控:OrbitControls 預設在 canvas 上設 `touch-action: none`,兩個堆疊的人形佔掉大半螢幕就**捲不過去**。改成一指捲頁、兩指旋轉縮放(`touches.ONE = null` 會落到 `default: state = NONE`),右下角有「雙指旋轉・縮放」提示 —— 不講沒人會發現
- ⚠️ **`renderer.setSize(w, h, false)` + `height: 100%` + 沒有確定高度的祖先 = canvas 尺寸失控**:setSize 會把 canvas **屬性**高度寫成 `h × devicePixelRatio`,而 `height:100%` 解不出來時 canvas 改用屬性高度當內在高度 → 容器變高 → ResizeObserver 再放大一次 DPR。實測手機版 1857px、1280px 寬的 1.25× 螢幕 3647px(應為 685)。**DPR=1 的螢幕剛好是穩定不動點,所以它藏了很久**。修法是把 canvas 設成絕對定位,讓它結構上不可能把自己的尺寸餵回版面
- 三態顯示的初始值:只開「目前」(綠色),基準與預估都關閉 —— 三個一起疊在還不知道各是什麼的時候太難讀
